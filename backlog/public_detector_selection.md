- input: 公開Notebook、参照コード、重みのmetadataと学習来歴、公開結果の記録、Kaggleの資源制約。
- target / objective: 固定検出器の下流を学習できる具体的な構成を比較し、根拠付きの選定案を作る。
- output: NotebookのURLと版、重みの所在・版・SHA、検出と接続に使うモデルの対応、元の時間窓・前処理・特徴抽出箇所、トラッカー初期値案、来歴、費用の根拠と未確認事項、選定理由。
- loss: なし。選定では検出器・トラッカーを学習しない。
- decode / 推論方法: 公開構成の検出・接続・復号・後処理を分けて記録し、初回の比較対象とする構成を特定する。候補の動作確認が必要な場合は元の公開条件を使い、改良を同時に加えない。
- 処理単位: Notebookの版と、その版が参照するcheckpoint・前処理・下流モデルの組。
- 実装区分: 選定調査。参照構成を省略・変更する場合は実際の差分を記録し、元の公開スコアの再現と同一視しない。

## 親実験からの差分

- 変更するもの: 未指定だった公開検出器・特徴抽出器と、基準トラッカーの具体的な版を選定する。
- 固定するもの: 公開検出器・画像特徴抽出器を更新せずトラッカーを学習する方針、Kaggle Notebookのみ・GPU週30時間以内・課金なし、既存の評価方針。
- 再利用するコード / config / 生成物: 保存済み公開調査とそこから参照するNotebook・metadata。既存の自前結果は補助情報として区別する。
- 新しく作るもの: 公開構成の比較表、推奨する具体的な版と根拠、後続の特徴保存・基準推論に渡す入力仕様。完了した調査はdocs/surveysへ記録する。

## 最小の反証可能な検証

- 検証方法: 保存済み資料から候補を絞り、参照コード・checkpointの取得可能性、モデルの対応、学習来歴、元の時間窓での特徴取得を確認する。公開結果は全構成の報告として扱い、特徴抽出時間・候補数・保存量の根拠と未測定部分を記す。静的確認で決まらない動作や費用は、小規模なKaggle確認の条件を具体化してから実行判断へ渡す。
- variant / config / fold / booster数: 保存済み公開調査に含まれる構成を入口とし、同一checkpointを参照するNotebookはモデル重複を識別する。全候補の学習・追加seed・両胚フル推論を選定の必須条件にしない。
- control再学習: なし。選定のために自前検出器や全層更新の対照を学習しない。
- 想定runtime / resource: コード・metadata比較はGPU不要。小規模な動作・費用確認が必要ならKaggleの残量内で対象と上限を決める。全件の特徴保存と反復費用の実証はexact_window_cacheへ渡し、選定の依存を循環させない。

## 成功条件と停止条件

- primary指標: 具体的な版と取得可能性、特徴とトラッカー入力の互換性、学習来歴、費用の根拠。報告された公開スコアは補助情報とする。
- 成功条件: 推奨するNotebook・重みの組を一意に指定でき、固定対象と下流学習への渡し方、判断理由・未確認事項を提示できる。ユーザーの選定判断後に方針と後続候補へ具体的な参照を反映する。
- 必須guard: Notebookのタイトルや重みのファイル名だけで学習履歴を推定しない。学習来歴不明または評価胚を含む重みを独立評価済みと扱わない。複数モデル・後処理込みのスコアを単独検出器の精度と呼ばない。
- 成功時の次段階: 選定根拠と限界を示し、確定した公開構成をexact_window_cache、公開基準の診断、frozen_image_encoderへ渡す。トラッカーの学習・submissionは自動で開始しない。
- 失敗時の停止範囲: 条件を満たさない理由をモデルごとに記録し、同じ方針内の他の公開構成を調べる。検出器の自前学習や外部GPU利用へ切り替えない。

## 実行しないこと

- 禁止する代替実装、proxy、同一OOF上の救済探索: タイトルの最高スコアだけで選ぶ、公開重みを自前重みで代用する、特徴の保存・再学習の完了を待たないと選定できない依存を作ること。
- 壁打ちで採らなかった案と理由: 選定を複数候補の未決事項だけに残す管理は、実施順と成果の引き継ぎが不明確になるためやめる。全公開モデルの再学習による順位付けは固定方針と予算に合わない。

## リスク

- leakage / validation: 公開checkpointに評価胚が含まれる・来歴不明の場合は、条件付き比較として後続へ明示する。
- hidden test: 公開ページの実行時間だけではhidden全件の完了を保証できない。元の推論入力と全件処理条件を確認する。
- runtime / memory: 特徴次元・時間窓・候補数と複数モデルの有無で費用が変わる。静的な概算、公開報告、自分たちの実測を区別する。
- 再現性: Notebook・コード・checkpointの版を対応付ける。現在の学習方針を正とし、過去の自前学習方針へ戻さない。

## 調査で確認する事項

- 実際に取得できるNotebook・checkpointの版、学習来歴と利用条件、特徴取得方法、基準トラッカーとの対応。
- 公開構成間の違いと推奨を決める根拠。取得・特徴入力の互換性と固定方針への適合を確認し、来歴の確かさ、費用の根拠、公開結果を比較する。根拠不足の場合は未確認と記録し、モデルを選定済みと扱わない。
- 静的情報だけで動作・費用を判断できない場合に必要なKaggle確認の対象と実行費用。追加実行が必要と分かった時点で条件を具体化し、資料・コードの調査開始をその確定待ちにしない。

これらは本候補の調査対象・成果であり、調査を設計する前に解消する条件ではない。選定案の確定判断は根拠提示後に行い、調査開始の前提にしない。公開検出器固定・トラッカー学習・週30時間の共通方針は承認済み。
